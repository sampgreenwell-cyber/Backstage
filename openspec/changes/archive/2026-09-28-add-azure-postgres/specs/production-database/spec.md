# Spec Delta

## Purpose

Defines the managed PostgreSQL database that backs production Backstage: how it is provisioned as code at the lowest workable cost, how it is secured, and how the Container App connects to it.

## ADDED Requirements

### Requirement: Production database is provisioned as code at the cheapest workable tier
The production database SHALL be an Azure Database for PostgreSQL Flexible Server defined in the `infra/terraform/azure-container-apps` Terraform module, in the same resource group as the Container App. Its region SHALL be configurable independently of the Container App's, because Azure restricts Flexible Server provisioning in the Container App's region (`eastus`) for this subscription; it defaults to `eastus2`. It MUST use the Burstable B1ms compute tier, PostgreSQL 16, the 32 GB storage minimum with storage auto-grow disabled, 7-day backup retention, and MUST NOT enable high availability or geo-redundant backups.

#### Scenario: Server matches the cheapest configuration
- **WHEN** the operator runs `az postgres flexible-server show` against the provisioned server
- **THEN** it reports SKU `Standard_B1ms`, tier `Burstable`, version `16`, 32 GB storage, high availability disabled, and geo-redundant backup disabled

#### Scenario: Terraform converges
- **WHEN** the operator runs `terraform plan` immediately after a successful `terraform apply`
- **THEN** the plan reports no changes

### Requirement: Adding the database does not disturb existing infrastructure
Introducing the database MUST only add resources. It MUST NOT change, replace, or destroy any existing resource in the module, and MUST NOT cause Terraform to manage the Container App's `secret` or `env` lists.

#### Scenario: Plan is additive only
- **WHEN** the operator runs `terraform plan` against current remote state with the change applied to the module
- **THEN** the summary shows only additions and `0 to change, 0 to destroy`

#### Scenario: Manually set Container App secrets survive
- **WHEN** Terraform is applied after `DATABASE_URL` and `BACKEND_AUTH_SECRET` have been set manually on the Container App
- **THEN** those secrets and environment variables remain present and unchanged

### Requirement: Database credentials are generated, not hand-written
The database administrator password SHALL be generated by Terraform and retrievable only as a sensitive output. It MUST NOT be committed to the repository or stored in any checked-in config file.

#### Scenario: Operator retrieves credentials to build the connection string
- **WHEN** the operator runs `terraform output -raw` for the database admin password and server FQDN
- **THEN** they obtain the values needed to build a `postgresql://` connection string, and `terraform output` without `-raw` shows the password as sensitive

### Requirement: Connections are encrypted and network access is restricted
The server SHALL require TLS for all client connections. Network access MUST be limited to Azure services (for the Container App) by default; any access from an operator's workstation MUST be a temporary firewall rule that is removed after verification and is not tracked in Terraform.

#### Scenario: Non-TLS connection is rejected
- **WHEN** a client connects with `sslmode=disable`
- **THEN** the server rejects the connection

#### Scenario: Temporary operator access leaves no residue
- **WHEN** verification is complete and the temporary workstation firewall rule has been deleted
- **THEN** `az postgres flexible-server firewall-rule list` shows only the Azure-services rule, and `terraform plan` reports no changes

### Requirement: Production Backstage runs on the Azure database
The live Container App's `DATABASE_URL` SHALL point at the Azure Flexible Server, set manually as a Container App secret (not through Terraform). Backstage MUST start against a fresh database, create its own per-plugin databases, and serve the catalog and GitHub sign-in.

#### Scenario: Backstage starts healthy on the new database
- **WHEN** the `database-url` secret is updated to the Azure connection string and a new revision starts
- **THEN** the revision reports Running/Healthy and the container logs contain no database connection errors

#### Scenario: Backstage creates its schema on a fresh database
- **WHEN** Backstage has started against the empty server
- **THEN** listing databases on the server shows `backstage_plugin_*` databases created by Backstage

#### Scenario: Core user flows work
- **WHEN** a user opens the production app URL
- **THEN** GitHub sign-in succeeds and the catalog lists the entities from the configured `catalog.locations`

### Requirement: CI plan remains green
The existing CI `terraform plan` job SHALL continue to succeed after the database is added and applied, using the CI service principal's existing permissions.

#### Scenario: First CI run after apply
- **WHEN** a commit is pushed to `main` after the database has been applied
- **THEN** the `Terraform plan` job succeeds, including refresh of the new database resources
